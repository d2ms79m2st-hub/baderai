# تقرير تجربة ترحيل الكتالوج

## بيئة الاختبار

تم إنشاء مشروع Supabase منفصل مجاني باسم `baderai-catalog-test`، بالمعرّف `qmabnkihvfymoksmcvit`، في منطقة `eu-central-1`. التكلفة المعروضة للمشروع هي صفر شهريًا. لم يُستخدم مشروع `baderai-auth` في أي خطوة.

لأن المشروع الجديد لا يحتوي بنية المصادقة الخاصة بالمشروع الإنتاجي، أُضيفت فيه بنية اختبار مؤقتة محدودة: جدول `public.profiles`، ومخطط `private`، ودالة `private.is_admin()` المطابقة لمنطق الإنتاج. أُدخل حسابان اختباريان كصفوف profile فقط، ولم تُنشأ حسابات Auth حقيقية ولم تُستخدم كلمات مرور.

## ما نُفّذ فعليًا

نجح تطبيق migration على المشروع الاختباري بعد تهيئة دالة المدير التجريبية. أُدخل منتج متاح ومنتج نافد، وتصنيف وعلاقات وصور ولقطات أسعار.

القراءة بدور `anon` أعادت المنتج المتاح فقط، ولم تُظهر المنتج النافد. التصنيف والصورة العامة ظهرا فقط عبر العلاقة العامة. القراءة بدور `authenticated` مع claim لمستخدم غير مدير أعادت المنتج العام فقط. القراءة بدور `authenticated` مع claim لصف admin أعادت المنتجين، بما فيه السجل غير العام.

فشلت الكتابة بدور `anon`، وفشلت الكتابة لمستخدم authenticated غير مدير، ونجحت كتابة المدير داخل معاملة اختبارية ثم جرى التراجع عنها. هذه اختبارات PostgreSQL فعلية باستخدام أدوار قاعدة البيانات وclaims اختبارية؛ ليست تسجيل دخول Auth كاملًا بحسابين حقيقيين.

نجحت القيود التالية فعليًا: منع `available=true` مع `out_of_stock=true`، منع تقييم 9، منع علاقة بتصنيف غير موجود، منع تكرار لقطة السعر نفسها، والحذف المتسلسل للصورة عند حذف المنتج.

تم اختبار rollback فعليًا. المحاولة الأولى كشفت اعتماد سياسات RLS على جداول العلاقة، فتم تعديل rollback ليحذف سياسات الترحيل أولًا. بعد التصحيح نجح rollback، وحُذفت جداول الكتالوج الخمسة فقط، وبقي `public.profiles` الاختباري وفيه صفان.

## ما لم يُنفّذ

لم تُطبق migration على `baderai-auth` الإنتاجي. لم يتغير مصدر الكتالوج أو واجهة المتجر، ولم تُنشأ جداول السلة أو الطلبات أو الدفع أو الشحن. لم تُنشأ حسابات Auth حقيقية، لذلك لا أدّعي اختبار تدفق تسجيل دخول كاملًا أو اختبارًا بحسابي مستخدم ومدير فعليين.

## الخطوة الإنتاجية المعلقة

الملف `supabase/migrations/20261025001000_create_catalog_tables.sql` جاهز للتطبيق على المشروع الإنتاجي بعد موافقة صريحة. قبل التطبيق يجب أخذ نسخة احتياطية، والتحقق من عدم وجود جداول تحمل الأسماء نفسها، ثم تطبيق migration ومراجعة الجداول والسياسات. لا يُشغّل rollback إلا بموافقة تشغيلية منفصلة لأنه يحذف بيانات جداول الكتالوج.
